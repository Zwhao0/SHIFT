## 优化顺序

1. **先补齐恢复关键路径计时，建立新基线。** 保留单控制器时钟的完整请求→16逻辑rank共同提交；另列请求→候选import/model/build/warmup/channel ready、实际cut、冻结/快照/hash/传输/restore/验证/decision/重连/activation/首提交和健康副本等待。worker只计算本机耗时，禁止跨主机monotonic相减。报告准备期间提交数、最长共同提交间隔、首步及后续窗口，区分“训练继续推进”和“停止推进”。仅在迁移边界加轻量事件，性能窗口不增加逐步hash。

2. **首要改动是分离开发审计与正式路径。** v4.1只关掉逐步hash，迁移边界仍无条件全状态hash，且`Transaction.candidate()`把九类hash一致性直接当准入条件。需要显式审计策略贯通snapshot、restore、候选报告、peer恢复和切换后检查，不能只传空hash或伪造相等签名绕过现有事务。

   正式路径不执行开发用途的全量九状态hash、独立梯度参考、冗余全状态遍历和调试日志。运行必需的schema/实际cut/epoch/逻辑rank/owner检查、完整字段与张量结构检查、严格restore、四候选成功确认、全局commit fencing、超时回退和全部actor排空仍保留；传输和状态隔离必需的复制保留。候选必须实际完成恢复与必要检查后才可报告成功，不能把“收到packet”当“可接管”。

   开发模式在同一训练和交接实现周围启用完整九状态、梯度、轨迹与错误注入校验；正式模式结果在计时窗口结束后另做完整最终审计。显式区分错误检测范围：任意静默状态篡改的逐字节检测属于审计模式，不能宣称正式轻量路径也保留相同检测能力。正式模式仍需拒绝缺字段/旧版本/错误角色/恢复异常，超时必须retain或按既有源失联范围fail-stop。

   A0快照与再次freeze hash两个区间各约1.15秒，但含clone/同步；正式模式可回收部分需实测。其余rank重叠，不能按调用数累加收益。区分A=已发布v4.1，B=正式路径去开发审计，C=B加其他优化；报告A→B策略成本变化及B→C实现收益。

3. **开发模式合并重复hash；staged digest降为辅助优化。** snapshot后freeze再次hash；候选恢复前hash、restore内部hash及返回后hash均需审查。只有同一冻结状态无写入时复用结果，故障注入修改后重新hash；重连/RNG恢复后仍独立验证，不跨步缓存。已有`state_digest.py`的有界staged实现可显式接入开发入口，先证明SHA逐字节一致，再比较审计耗时。正式恢复优化不依赖更快hash，不把加速开发工具当生产吞吐收益。

4. **再优化候选冷准备。** 请求→边界占10.0/16.5秒，其中包含预定cut等待、候选准备和边界量化，不能全部算冷启动。分项确认后，在同一冷启动语义下尝试CPU模型加载与本地group准备重叠，或减少完整模型加载/分片构造的无用工作。现有备用本地warmup、状态通道预连接、TP/EP组复用和Manager保留已启用，不重复作为新优化。提前启动热备用只能单列warm-standby实验，预备成本仍记入总账，不能替代冷启动主成绩。

5. **最后检查激活路径。** 测量`gc.collect()/empty_cache()`、group关闭/连接、outer首次quorum与PP首次通信；只有明确位于关键路径且有净收益才改。释放anchor后能否把GC/allocator清理移出首提交之前，必须证明0.12显存上限内无峰值回归、旧owner及失败候选完整收尾。A0 connect仅0.26–0.42秒，暂不重写通信管理。5ms全局提交投票轮询先保持。

## 实验、验收与止损

- 每轮先prepare；单`runtime/v3-training.lock`、GPU严格串行、既有环境/模型/headers与0.12显存上限不变，不操作公司共享容器。
- raw已清理，先新建匹配独立参考，覆盖实际cut及后续步；旧精简签名仅用于定位与来源核对，不能代替raw verifier。改动在新`codex/`分支，保留v4.1基点。
- 首先一例原版轻量分项基线；每个候选先跑相关CPU协议/签名/参数透传测试及一次同seed探索配对，无可信净收益则不扩大矩阵。
- 候选最终开发审计至少两个不同seed/触发点，完整九状态、独立梯度、样本、owner、成员、提交和健康PID；恢复后至少5共同提交。开发模式测静默篡改被hash拒绝；正式模式另测实际恢复异常、结构/版本错误、受控超时retain，以及源冻结后失联的既有回退范围。必须等全部actor四device终态。
- 有效候选与v4.1同seed/触发/cut规则/slow_ms/冷启动语义做ABBA交错性能比较，显式披露A→B审计策略变化；其他优化在同为正式模式的B/C之间比较。正式计时窗口无开发全状态hash，结束后做完整九状态审计。全部慢样本保留，报告每run完整恢复时间、实际cut、准备期间步数、共同提交停顿及观察开销。明显收益再补第二seed交错组；run作为重复单位。
- 优化目标暂定完整恢复改善≥10%，且改善超过配对波动；这是筛选目标，不是已有收益。若只有轮询观察时间变短、真实共同提交停顿未改善，单列为控制器优化。共享负载阻止判断时结论为未证实。
- 最终检查恢复后步时：新建迁移后跨节点PP布局控制，候选/基点匹配较长窗口（80步，固定11–80统计，同时保留完整1–80）；若用户后续只要求快速功能回归，短窗口不能宣称稳定吞吐改善。必要时补新v1/v2性能对照，不用跨负载旧结果宣称超越。
- 同一路线约3次配对仍无可信收益、数值/回退失败或资源异常即停止该路线；不靠放宽期限、减少实际恢复的九状态内容或开发审计字段、缩短排空或筛掉慢样本取得成绩。
- 收尾导出精简结果、限制、来源SHA与seed/manifest，然后删除可再生raw/log/trace/中间快照，核查SHIFT进程/unit/额外GPU占用为0、公司PID保持；保留必要源码、环境、私有配置、比较签名和最小BF16初始anchor。
